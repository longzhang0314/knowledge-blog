# 缓存一致性的常用方案

## 结论

大多数业务不追求缓存和数据库强一致，而是通过 Cache Aside、过期时间、消息补偿和监控把不一致窗口控制在可接受范围内。

## 常见写法

```java
updateDatabase(command);
deleteCache(cacheKey);
```

优先更新数据库，再删除缓存。原因是数据库是最终事实来源，缓存删除失败可以通过重试、消息补偿或过期时间修复。

## 风险

- 删除缓存失败导致旧值长时间存在。
- 并发读写下旧值被重新写回缓存。
- 热点 key 删除后瞬时打到数据库。

## 兜底

为关键缓存删除增加重试和告警；为热点 key 增加互斥重建或逻辑过期；为一致性要求更高的场景增加 binlog 或消息驱动的补偿链路。

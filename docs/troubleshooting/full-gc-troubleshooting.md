# Full GC 频繁排查总结

## 结论

Full GC 本身不是问题，**频繁 Full GC、单次停顿过长、Full GC 后老年代回收不明显**才是真正需要处理的线上风险。

排查时不要一上来就调 JVM 参数。更稳的思路是：先确认业务是否受影响，再判断是老年代占用下不来、瞬时大对象冲击、内存泄漏、元空间增长，还是 GC 策略和堆大小不匹配。

## 一、先止血

线上出现 Full GC 告警时，先看它有没有影响核心链路：

- 接口 RT 是否明显升高，错误率是否上升。
- 机器 CPU、Load、内存、网络是否同时异常。
- Full GC 是否集中出现在某个发布、定时任务、流量高峰或大批量操作之后。
- 是否有单机异常，还是整个集群同时异常。

如果已经影响可用性，优先做止血动作：

- 临时扩容实例，分摊流量和对象创建压力。
- 对非核心入口限流、降级或暂停大批量任务。
- 如果和刚发布版本强相关，优先回滚。
- 保存现场：GC 日志、堆 dump、线程 dump、监控截图、发布记录和关键业务操作记录。

## 二、再定位

### 1. 先看 Full GC 的形态

重点看三个指标：

- **频率**：几分钟一次、几十秒一次，还是持续循环。
- **耗时**：单次停顿几十毫秒、几百毫秒，还是几秒以上。
- **回收效果**：Full GC 后老年代占用是否明显下降。

如果 Full GC 后老年代下降明显，通常说明是瞬时对象或批量任务导致的高峰；如果下降不明显，要重点怀疑长期存活对象、缓存膨胀或内存泄漏。

### 2. 看 GC 日志和堆状态

常用命令：

```bash
jstat -gcutil <pid> 1000 10
jcmd <pid> GC.heap_info
jcmd <pid> VM.flags
```

如果需要保存现场：

```bash
jcmd <pid> GC.heap_dump /tmp/app-fullgc.hprof
jmap -histo:live <pid> | head -50
```

重点观察：

- 老年代使用率是否持续走高。
- Full GC 后老年代是否仍然很高。
- 元空间是否持续增长。
- 是否有大量同类型对象、超大集合、缓存对象或字符串对象。

### 3. 找业务入口

Full GC 很多时候不是 JVM 参数问题，而是业务对象生命周期问题。常见入口包括：

- 一次性查询过多数据，比如导出、报表、批处理、深分页。
- 本地缓存没有容量上限或淘汰策略。
- 线程池队列堆积，任务对象长期无法释放。
- 大对象频繁创建，比如大 JSON、大集合、文件字节数组。
- 定时任务集中运行，短时间制造大量对象。
- 动态代理、脚本、类加载异常导致元空间增长。

定位时要把 GC 时间点和业务日志、接口调用量、定时任务、发布记录对齐。只看 dump 不看业务时间线，很容易只看到结果，看不到触发原因。

## 三、常见根因判断

| 现象 | 常见原因 | 处理方向 |
| --- | --- | --- |
| Full GC 后老年代明显下降 | 瞬时大流量或批任务 | 限流、分页、分批处理、错峰执行 |
| Full GC 后老年代下降很少 | 长生命周期对象过多或泄漏 | 分析 dump，查缓存、集合、静态引用 |
| 元空间持续升高 | 类加载过多或动态生成类异常 | 查动态代理、脚本引擎、热加载 |
| Full GC 伴随 CPU 升高 | GC 线程消耗或应用线程竞争 | 看 GC 日志、线程 dump、CPU 火焰图 |
| 老年代增长和发布强相关 | 新代码引入对象持有 | 回滚或定位新版本对象引用 |

## 四、项目落点

如果面试或复盘中被问到 Full GC，我会按这个顺序讲：

1. **先判断影响**：看 RT、错误率、核心链路和告警范围，必要时扩容、限流或回滚。
2. **保存现场**：保留 GC 日志、堆 dump、线程 dump、监控和发布记录。
3. **看回收效果**：Full GC 后老年代是否下降，这是区分瞬时压力和疑似泄漏的关键。
4. **查对象来源**：通过对象直方图和 dump 分析大对象、缓存、集合、队列和业务引用链。
5. **对齐业务时间线**：把 Full GC 时间点和接口流量、定时任务、批处理、发布变更对应起来。
6. **复盘治理**：补容量评估、限流降级、分页批处理、缓存上限、队列监控和 GC 告警。

## 五、复盘治理

治理 Full GC 不能只写“调大堆内存”。堆调大只能缓解一部分容量问题，如果根因是泄漏或无界缓存，堆越大只是让问题晚一点爆发。

复盘时建议补齐：

- 核心接口 RT、错误率、Full GC 频率和耗时的告警。
- 缓存容量上限、过期策略和命中率监控。
- 批处理、导出、报表类任务的分页和限速。
- 线程池队列长度、拒绝次数和任务耗时监控。
- 发布后 JVM 指标观察窗口，避免新版本引入内存风险。

最终目标不是“以后没有 Full GC”，而是让 Full GC 可观测、可解释、可止血、可复盘。

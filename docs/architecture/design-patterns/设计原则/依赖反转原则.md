### 依赖反转原则

1. **控制反转**：

控制反转是一个笼统的设计思想，用来指导框架层面的设计。控制指的是对整个程序流程的控制，反转指的是原本对于整个流程的控制是由程序员来做，反转以后交给框架来处理。


- 对于一个测试框架，使用控制反转前：
```
public class UserServieceTest &#123;

    public static boolean doTest() &#123;
        return true;
    &#125;

    public static void main(String[] args) &#123;
        //程序员控制流程
        if (doTest()) &#123;
            System.out.println("Test sucessed");
        &#125; else &#123;
            System.out.println("Test failed");
        &#125;
    &#125;
&#125;
```
- 使用控制反转以后：
```
public abstract class TestCase &#123;
    
    //不同的测试框架在此处进行扩展
    public abstract boolean doTest();

    //程序流转的逻辑抽取出来
    public void run() &#123;
        if (doTest()) &#123;
            System.out.println("Test sucessed");
        &#125; else &#123;
            System.out.println("Test failed");
        &#125;
    &#125;
&#125;

//对测试框架具体功能点进行扩展，不对程序流转逻辑做改变
public class UserServiceTest1 extends TestCase &#123;
    @Override
    public boolean doTest() &#123;
        return false;
    &#125;

&#125;


public class JunitApplication &#123;
    //把所有的测试具体测试框架实现放入容器中
    private static final List&lt;TestCase> testCases = new ArrayList&lt;>();

    public static void register(TestCase testCase) &#123;
        testCases.add(testCase);
    &#125;

    static &#123;
        register(new UserServiceTest1());
    &#125;

    public static void main(String[] args) &#123;
        for (TestCase testCase : testCases) &#123;
            testCase.run();
        &#125;
    &#125;
&#125;


```
这样，通过类似模板设计模式的方法实现了对测试框架流程的控制反转。

2. **依赖注入**：

依赖注入是控制反转的实现方式之一，是一种具体的编码技巧。我们不使用在类内部new出需要依赖对象的方法，而是在外部创建好对象，需要使用依赖对象时直接进行构造方法，或者方法参数传递等方式进行引入即可。

- 非依赖注入方式：
```
public class Notification &#123;

    private MessageSender messageSender;

    public Notification() &#123;
        this.messageSender = new MessageSender();
    &#125;

    public void sendMessage(String cellPhone,String message) &#123;
        //...校验逻辑
        this.messageSender.send(cellPhone,message);
    &#125;

    public static void main(String[] args) &#123;
        //无法对MessageSender进行扩展
        Notification notification = new Notification();
        notification.sendMessage("cell","mess");
    &#125;
&#125;
```
- 依赖注入方式：
```
public class Notification2 &#123;

    private MessageSender messageSender;

    public Notification2(MessageSender messageSender) &#123;
        this.messageSender = messageSender;
    &#125;

    public void sendMessage(String cellPhone,String message) &#123;
        //...校验逻辑
        this.messageSender.send(cellPhone,message);
    &#125;

    public static void main(String[] args) &#123;
        //提前创建好messageSender对象，提高了代码的扩展性
        MessageSender messageSender = new MessageSender();
        Notification2 notification2 = new Notification2(messageSender);
        notification2.sendMessage("cell","mess");
    &#125;

&#125;
```
- 依赖注入方式的扩展：
```
public class Notification3 &#123;

    private IMessageSender iMessageSender;

    public Notification3(IMessageSender iMessageSender) &#123;
        this.iMessageSender = iMessageSender;
    &#125;

    public void sendMessage(String cellphone, String message) &#123;
        this.iMessageSender.send(cellphone, message);
    &#125;

    public static void main(String[] args) &#123;
        //提供扩展性
        //但此处创建对象的工作依然是硬编码，所以之后产生了依赖注入框架
        IMessageSender iMessageSender = new SmsSender();
        Notification3 notification3 = new Notification3(iMessageSender);
        notification3.sendMessage("cell","mess");
    &#125;
&#125;
```

3. **依赖注入框架**

依赖注入框架：只需要定义类与类之间的依赖关系，由框架来实现自动创建对象，管理对象生命周期，依赖注入等原本需要程序员来做的事。

4. **依赖反转原则**

依赖反转原则：主要用来指导框架层面的设计，高层模块不依赖底层模块，他们都依赖同一个抽象（例如，tomcat不依赖具体的web实现，他们都依赖servlet规范）；抽象不依赖具体实现，具体实现依赖抽象。


---

控制反转的本质是分拆控制代码和具体执行代码，控制代码放在较高的层次上，也可能交给第三方类库，实现代码放在较低的层次上，通常是一个接口的实现。

依赖反转本质是分拆类中的new语句，因为new语句引入了对实现类构造函数的依赖，属于很强的依赖。分拆之后构造和实现放在另外一个类里（通常交给第三方类库），使用的地方引用接口。依赖反转可以拆分类的依赖关系，可以减少实现类的引用，用接口取代，实现接口和实现的分离。依赖反转和基于接口而非实现的原则类似，两者都倾向于依赖接口而非具体类。不同点在于，前者更关注类层次中的依赖关系以及对构造函数的依赖，尽量避免高层次的类依赖底层的实现，尽量避免对构造函数的依赖。后者，更强调类的使用的地方，尽量使用更抽象更宽泛的接口，而非更具体更细节的实现，使得信息隐藏和抽象。

控制反转和依赖反转都是有成本的，会破坏代码的内聚性和简洁性，需要权衡使用
